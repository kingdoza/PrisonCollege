# PrisonCollege 튜토리얼 코드 구현 프롬프트

아래 지시를 현재 `PrisonCollege` Unity 프로젝트의 튜토리얼 코드 구현 작업에 사용한다.

## 역할과 목표

`C:\UnityProjects\PrisonCollege`에서 신임 교수 연수 튜토리얼의 런타임 코드를 구현한다.

구현의 최우선 조건은 다음 두 가지다.

1. 확정된 튜토리얼 정책을 임의 해석 없이 구현한다.
2. 기존 파일을 수정하더라도 정규 스테이지, 메인 메뉴, 상점, 아레나와 기존 학생 AI의 동작에는 영향이 없어야 한다.

튜토리얼은 기존 시스템을 파괴적으로 개조하는 기능이 아니라, 전용 씬에서 기존 시스템의 공개 포트를 통해 동작하는 별도 실행 모드여야 한다.

## 기준 문서와 결정 우선순위

작업 전에 아래 문서를 처음부터 끝까지 읽는다.

1. `.md/TUTORIAL_POLICY_DECISIONS.md`
2. `.md/TUTORIAL_FUNCTIONAL_DESIGN.md`
3. 이 프롬프트

게임 정책의 우선순위는 다음과 같다.

```text
사용자가 작성한 P/T 결정값
  > 최초 요구사항 R
  > 기능 설계의 기술 제안
  > 구현 편의를 위한 추정
```

문서 사이에 충돌이 있으면 위 순서를 적용한다. 결정되지 않은 정책을 코드 작성자가 선택해서는 안 된다.

현재 Unity Editor 설정 대기 항목은 다음과 같다.

- `P-23`: 6단계 작업 확인 시간 `n`의 실제 값은 Unity Inspector에서 사용자가 설정한다.
- `P-28`: 8단계 고정 장비, 슬롯 순서, 탄약, 보충 시설과 비용은 Unity Inspector에서 사용자가 설정한다.
- `P-29`: 미니웨이브 `BehaviorWeightSet` asset과 행동별 가중치는 Unity Inspector에서 사용자가 설정한다.

이 값들을 임의의 숫자나 asset으로 채우지 않는다. 단, 정책문서에 기본값이 명시된 8단계 제한 시간 30초, 탈출 실패 기준 3명, 학생 수 4명은 그 기본값을 사용할 수 있다.

## 절대적인 기존 동작 비회귀 원칙

아래 조건을 위반하는 구현은 완료로 간주하지 않는다.

### 1. 기본 실행 경로 보존

- 새 튜토리얼 모드가 명시적으로 활성화되지 않은 경우 모든 기존 클래스는 현재와 같은 정규 실행 경로를 사용해야 한다.
- 새 bool, enum, config 또는 strategy의 기본값은 반드시 정규 스테이지 동작이어야 한다.
- 기존 씬에 새 참조가 연결되지 않아도 정규 스테이지가 예외 없이 실행돼야 한다.
- 기존 `Awake`, `Start`, `Update`, 애니메이션 이벤트와 UnityEvent 호출 순서를 불필요하게 바꾸지 않는다.
- 기존 public 메서드의 의미, 매개변수와 Unity Inspector 이벤트 연결을 깨지 않는다.

### 2. 기존 데이터 보존

- 정규 `BehaviorWeightSet`, `BoostData`, 무기 데이터, 학생 프리팹과 스테이지 설정값을 튜토리얼 값으로 수정하지 않는다.
- 기존 serialized field의 기본값을 바꾸지 않는다.
- 기존 씬, 프리팹, Animator Controller, ScriptableObject YAML을 코드 구현 과정에서 임의로 수정하지 않는다.
- 튜토리얼 전용 데이터가 필요하면 별도 타입이나 별도 asset용 정의를 추가한다.
- `WaveSystem`의 현재 웨이브나 정규 `InventorySystem`의 장비·자금을 튜토리얼 진입을 위해 변경하지 않는다.
- 튜토리얼 프로젝트 보상은 세션 내부 값으로만 관리하고 정규 인벤토리에 지급하지 않는다.

### 3. 기존 코드 수정 방식

- 기존 클래스를 통째로 튜토리얼 구조에 맞춰 재작성하지 않는다.
- 이벤트, 읽기 전용 상태, 제한된 제어 API와 명시적 runtime config를 추가하는 방식으로 확장한다.
- 튜토리얼 분기는 `isTutorial` 같은 전역 추측이 아니라 명시적으로 주입된 runtime config 또는 튜토리얼 전용 facade를 통해서만 활성화한다.
- 정규 경로의 조건식과 계산식은 가능한 한 그대로 둔다. 공통화가 필요하면 리팩터링 전후 결과가 동일함을 검증한다.
- 튜토리얼에서 기존 클래스의 private 필드나 `PostStudent.Blackboard`를 외부에서 직접 변경하지 않는다.
- 새 이벤트는 관찰 기능만 추가해야 하며 기존 이벤트 발생 횟수와 타이밍을 바꾸지 않아야 한다.
- 기존 상태가 실제로 변한 뒤에만 새 상태 변경 이벤트를 한 번 발생시킨다.
- 튜토리얼이 추가한 이벤트 구독, 코루틴과 임시 override는 단계 종료 및 오브젝트 파괴 시 반드시 해제한다.

### 4. 효과 차단 호환성

`EffectReceiver`에는 이미 `CanEffectChecker`와 `IsInvincible`이 있다. 대기·이동·복귀·응원 학생의 공격 및 부스터 차단을 위해 기존 수신 시스템을 별도로 복제하지 않는다.

`PostStudent`의 현재 정상 조건은 반드시 보존한다.

- 기존 부스터 수용 조건과 튜토리얼 학생 모드 조건을 AND로 결합한다.
- 기존 피해 수용 조건과 튜토리얼 학생 모드 조건을 AND로 결합한다.
- 튜토리얼 모드가 아닌 학생에게는 새 조건이 항상 `true`여야 한다.
- `CanEffectChecker`를 새 람다로 단순 덮어써 기존 탈출·행동 조건을 잃게 만들지 않는다.

### 5. 씬 및 에디터 작업 경계

`T-01`에 따라 `TutorialStage` 씬 생성과 오브젝트 배치는 사용자가 Unity Editor에서 수행한다.

코드 구현에서는 다음을 제공한다.

- 필요한 MonoBehaviour와 ScriptableObject 타입
- 명확한 serialized field와 tooltip
- 누락 참조를 식별할 수 있는 검증 메시지
- 사용자가 연결해야 할 Inspector 체크리스트

사용자의 별도 요청 없이 기존 씬·프리팹·Animator·asset을 직접 편집하지 않는다. 참조가 없는 상태를 임의 탐색이나 이름 기반 `Find()`로 메우지 않는다.

## 구현 구조

튜토리얼은 다음 방향으로 구현한다.

```text
TutorialStage
  -> TutorialSceneBootstrap
      -> TutorialDirector
          -> TutorialStepBase / 단계별 Step
          -> TutorialActorDirector
          -> TutorialCheckpointService
          -> TutorialHUDPresenter
      -> TutorialStageFacade
          -> 기존 StageController와 공개 API로 통신
```

### 핵심 책임

#### `TutorialDirector`

- 현재 `TutorialStepId`의 유일한 소유자다.
- 단계 `Enter -> Active -> Complete -> Exit` 순서를 보장한다.
- 같은 프레임에 완료 이벤트가 여러 번 들어와도 `CompleteOnce`로 한 번만 전환한다.
- 단계가 등록한 이벤트, 코루틴, 강조와 임시 제한을 `Exit`에서 정리한다.
- 표시 번호가 아니라 안정적인 enum ID로 단계를 관리한다.

#### `TutorialStageFacade`

- 튜토리얼 코드가 `StageController`, 학생, 탈출구와 시설을 직접 찾아다니지 않게 한다.
- 혼잡도, 변화율, 탈출, 프로젝트, 작업 인원, 교수 작업과 학생 상태를 읽기 전용으로 제공한다.
- 기존 시스템이 발행하는 이벤트를 튜토리얼용 의미 이벤트로 전달한다.
- 상태 초기화 메서드는 튜토리얼 runtime에서만 허용한다.

#### `TutorialActorDirector`

- `StudentDB`에 등록된 전체 학생을 한 번 생성하고 고정 대기 슬롯과 연결한다.
- 현재 DB 기준 9명이지만, 코드에 `9`를 로스터 배열 크기로 고정하지 말고 DB 개수를 사용한다. 단, 정책상 3단계는 현재 9명 중 8명을 요구하므로 설정 검증은 제공한다.
- 전체 학생 생성과 필수 참조 연결 후 각 학생의 튜토리얼 전용 행동 런타임 초기화 API를 한 번 호출한다.
- 전체 학생의 `Blackboard`와 루트 Behaviour Tree 초기화 호출이 동기적으로 반환된 뒤에만 `TutorialDirector`의 0단계 진입을 허용한다.
- 각 학생의 `Loyalty`, `Standby`, `TrainingTransit`, `Training`, `ReturnTransit`, `Cheer`, `MiniWave` 모드를 소유한다.
- `Loyalty`, `Standby`, `TrainingTransit`, `ReturnTransit`, `Cheer`에서는 초기화된 Behaviour Tree를 평가하지 않는다.
- 학생의 모드와 단계 참가 여부를 HUD 및 `StageController` 집계와 분리한다.
- 연수 진입과 복귀의 Warp·NavMesh 이동을 관리한다.
- 복귀는 단계 완료를 막지 않고 배경에서 계속 수행한다.

#### `TutorialCheckpointService`

- 8단계 최초 진입 시 의미 상태를 캡처한다.
- Behaviour Tree 및 NavMeshAgent 내부 객체를 직렬화하지 않는다.
- 재시작 시 플레이어, 장비, 혼잡도, 프로젝트, 탈출, 시간, 탈출구, 학생, 시설과 세션 자금을 최초 8단계 진입 상태로 다시 구성한다.
- 씬 시작 시 생성하고 초기화한 DB 전체 학생 풀은 8단계 재시작 때 파괴하거나 재스폰하지 않는다. 같은 학생 인스턴스의 체력, 위치, 모드와 행동 런타임을 동기적으로 reset한다.
- 8단계 재시작에서도 Ready 이벤트, polling 또는 준비 대기를 사용하지 않는다.
- 다른 단계의 현재 단계 재시작이나 일반 비정상 자동 복구는 구현하지 않는다.

#### `TutorialHUDPresenter`

- 표시만 담당하며 게임 상태를 판정하지 않는다.
- 단계별 제목, 목표, 안내, 완료 문구를 `TutorialCourseDefinition`에서 받는다.
- 목표가 수치형인 경우 `현재/목표`를 표시한다.
- 8단계 실패 화면에는 `8단계 다시 시작`, `건너뛰기`를 즉시 표시한다.

## 기존 클래스별 호환 구현 요구사항

### `StageController`

- 정규 runtime config를 기본값으로 사용한다.
- 정규 config에서는 현재와 동일하게 `WaveSystem`, `InventorySystem`, `RandomStudentSpawner`, 정규 승패와 상점/아레나 흐름을 사용한다.
- 튜토리얼 config가 명시적으로 주입된 경우에만 auto spawn, 타이머, 혼잡도 원인, 프로젝트, 탈출 실패와 finish policy를 튜토리얼이 제어할 수 있게 한다.
- `Start()`에서 튜토리얼 참조가 없다는 이유로 정규 스테이지 로직이 달라져서는 안 된다.
- 혼잡도 이벤트에는 원인을 구분할 수 있는 값이 있어야 한다. 최소 원인은 `ContinuousHazard`, `InnocentDown`, `Escape`, `Gunshot`, `NormalFoodRemoved`, `NaturalDecay`, `Reset`이다.
- 학생 등록/해제와 상태 이벤트를 추가하되 정규 학생 목록 집계 결과를 바꾸지 않는다.
- 튜토리얼 성공·실패에서는 정규 `StageOver`, 상점 이동, 웨이브 증가와 인벤토리 지급을 호출하지 않는다.

### `PostStudent`

- 기존 랜덤 Behaviour Tree가 기본이다.
- 정규 스테이지의 `StageStartEvent -> 기상 애니메이션 -> StartBehavior()` 호출 순서는 변경하지 않는다.
- 튜토리얼 전용 `InitializeTutorialBehaviorRuntime(...)` 공개 포트를 추가한다. 이 API는 필요한 참조를 받아 `Blackboard`와 루트 Behaviour Tree를 동기적으로 구성하고, 학생마다 한 번만 초기화되도록 중복 호출을 방지한다.
- 튜토리얼 초기화 API는 정규 `StartBehavior()`를 단순히 public으로 바꾸는 방식으로 구현하지 않는다. 정규 스테이지는 새 API를 호출하지 않아야 한다.
- 초기화 직후에는 행동 트리 평가를 멈춘 상태로 두고 `Training`의 지정 행동 또는 `MiniWave` 모드에서만 평가한다.
- 8단계 체크포인트 복원용 동기적 reset API를 제공하되 학생을 재스폰하거나 Ready를 다시 기다리지 않는다.
- scripted behavior 요청이 있는 학생만 지정 행동 경로를 사용한다.
- `BeginScriptedBehavior`, `ResolveScriptedBehavior`, `CancelScriptedBehavior`는 spot 해제, 협동 행동 탈퇴, 애니메이터·부착물 정리까지 일관되게 처리한다.
- 대기 모드와 이동 모드에서는 자율 행동, 피해, 부스터, 탈출, 작업, 혼잡도 원인과 집계를 차단한다.
- `Training`과 `MiniWave`로 전환된 뒤에만 해당 단계의 효과 대상이 된다.
- 3단계 동안만 자동 기상을 막고, 단계 종료 후 기존 자동 기상 설정을 복원한다.
- 3단계를 제외한 튜토리얼 학생의 체력과 자동 기상은 정규 학생과 동일하다.
- 정상 경로의 현재 `CanEffectChecker`, 행동 선택, 사망·기상 이벤트와 공격 로직을 보존한다.

### Behaviour Tree 코드

- 정상 랜덤 행동 노드를 변경하는 경우 튜토리얼 scripted request가 없을 때 기존 평가 결과와 부작용이 동일해야 한다.
- 3단계 해킹과 탈출구 공격은 연출만 수행하고 실제 조명 OFF, 바리케이드 피해와 탈출을 발생시키지 않는다.
- 이 억제는 해당 튜토리얼 시나리오에만 적용한다. 같은 행동이 정규 스테이지나 8단계 미니웨이브에서 실행될 때는 기존 결과를 유지한다.
- 행동 시작 텔레메트리는 enum이 선택된 시점이 아니라 학생이 spot에 도착해 실제 행동을 시작한 시점에 한 번 발생시킨다.

### `ExitGate`

- 설치·파괴 상태 변경 이벤트와 setup 전용 상태 설정 API를 추가한다.
- 정규 스테이지의 시작 시 랜덤 바리케이드 상태, 상호작용, 피해, 회복과 파괴 흐름은 그대로 유지한다.
- 튜토리얼 상태 설정 API를 정규 초기화 경로에서 호출하지 않는다.

### `ProfessorTask`

- 작업 시작·중단 이벤트, 중단 이유와 강제 중단 API를 추가한다.
- 기존 F 상호작용, 이동 입력 중단, 카메라와 모니터 연출은 그대로 유지한다.

### `StageSpots`

- 튜토리얼용 행동 지점을 Inspector에서 직접 연결하거나 안정적인 ID로 조회할 수 있게 한다.
- 정규 `GetRandomSpotByType()`와 현재 랜덤 spot 구성은 변경하지 않는다.

### `WeaponController`

- 정규 `EquipWeapon()`은 기존 인벤토리 기반 동작을 유지한다.
- 튜토리얼에서만 사용하는 별도 고정 loadout 적용 API를 추가한다.
- 장비 상태 snapshot/restore는 슬롯, 선택 인덱스와 탄약을 복원한다.
- 정규 장비 및 인벤토리 목록을 튜토리얼 목록으로 덮어쓰지 않는다.

### `CharacterRagdoll`

- 자동 기상 runtime override와 원래 값 복원 API만 최소 추가한다.
- override가 없을 때 기존 `_isAutoStandUp` 값과 기상 타이밍을 그대로 사용한다.

### `BoostData` / `BoostReceiver`

- 정규 `BoostData`의 기본 동작은 현재 패시브 보정 계산을 그대로 사용한다.
- 연수용으로 명시된 데이터에만 작업 100%, 광분 0%, 확률 패시브 보정 무시를 적용한다.
- 정규 fresh 부스터 asset을 수정하지 않는다.
- 투척 속도와 공격 동작 등 확률 외 수치는 정규 부스터와 동일한 데이터를 재사용할 수 있게 한다.

### `StudentDB`

- 전체 학생을 읽는 방어적 복사 또는 읽기 전용 API만 추가한다.
- 기존 `GetRandomStudentEntries()`의 셔플과 반환 의미를 변경하지 않는다.

### `GameManager`와 메인 메뉴

- `StartTutorial()`과 `ExitTutorialToMain()`을 정규 스테이지 진입과 분리한다.
- 튜토리얼 진입 시 현재 스테이지, 난이도, 웨이브와 인벤토리를 초기화하거나 변경하지 않는다.
- 튜토리얼 완료 여부만 별도 키로 저장한다.
- 8단계 건너뛰기도 완료로 기록한다.
- 재연수는 완료 기록을 지우지 않고 튜토리얼 처음부터 시작한다.
- 기존 `StartStage`, `PrepareStage`, `Restart`, `ShowMainScreen`, 스테이지 진행 저장의 의미를 변경하지 않는다.

## 단계별 필수 동작

세부 정책은 결정문서를 그대로 따르며, 아래는 구현 누락 방지를 위한 요약이다.

### 0~2단계

- 0단계 진입 전에 DB 전체 학생의 튜토리얼 행동 런타임 명시적 초기화 호출이 완료돼야 한다. 단계별 Ready 이벤트나 준비 대기는 없다.
- 0단계: DB 전체 학생 일렬 배치, 충성 자세, AI·이동·공격·부스터 차단, Tab 완료.
- 1단계: 충성 유지, 표시된 이동 Trigger 도착으로 완료.
- 2단계: 학생은 대기 공간 Idle, 모든 문·창문 강조, 현재 모든 출구에 바리케이드가 동시에 설치되면 완료.
- 0~1단계에서 미리 설치된 바리케이드도 2단계 진행도에 포함한다.

### 3단계

- 전체 학생 중 무작위 8명, 정상 4명과 위험 4명, 나머지 1명 대기.
- 정상/위험 쌍은 정책문서 `P-10`을 그대로 사용한다.
- 선택 학생은 출발 지점으로 Warp한 뒤 지정 지점까지 달려간다.
- 위험 학생 체력 0을 학생별 한 번만 카운트해 `0/4`를 진행한다.
- 정상 학생 오공격은 실제 피해만 적용하며 혼잡도·경고·진행도·복구를 발생시키지 않는다.
- 모든 혼잡도 증가를 차단하고 학생 공격 피해는 0으로 처리한다.
- 학생 체력은 정규 스테이지와 동일하다.
- 단계 안에서는 체력 0 학생이 자동 기상하지 않는다.
- 단계 종료 후 자동 기상을 복원하고, 기상한 학생은 배경에서 복귀한다.

### 4-1, 4-2단계

- 4-1은 3단계에 참여하지 않은 1명을 사용한다.
- 혼잡도 0에서 시작하고 모든 공격 수단을 인정한다.
- 실제 `InnocentDown` 혼잡도 증가와 HUD 반영을 모두 확인한 후 완료한다.
- 4-1부터 정규 자동 기상을 사용한다.
- 4-2는 현재 혼잡도를 유지하며 새 증가 원인을 막고 정규 감소 규칙을 사용한다.
- 감소 확인 전 Tab도 즉시 완료로 인정하고, 혼잡도 0도 완료 조건이다.

### 6, 7단계

- 6단계는 4-1에 참여하지 않았고 복귀 완료 후 현재 `Standby`인 학생만 선택한다.
- 연수용 부스터를 빈 슬롯에 최대 탄약으로 지급하고 자동 선택한다.
- 작업이 연속 `n`초 유지되면 완료한다. 끊기면 타이머를 0으로 되돌린다.
- 프로젝트가 먼저 완성되는 것은 허용하지만 `n`초 조건을 대체하지 않는다.
- 완료 즉시 학생 작업을 중단하고 배경 복귀시킨다.
- 7단계는 프로젝트 0에서 시작하고 학생 부스터 수용·학생 작업을 막는다.
- 교수 기여만으로 프로젝트가 한 번 완성되면 완료한다.

### 8단계

- 첫 진입 상태를 체크포인트로 저장한다.
- 전체 학생 중 설정된 `n`명을 무작위로 선택한다.
- 선택 학생은 연수와 동일한 출발 지점으로 Warp한 직후 `MiniWave` 행동을 시작한다.
- 선택되지 않은 학생은 대기 공간에서 응원 자세를 유지하며 모든 효과와 집계에서 제외한다.
- 제한 시간, 탈출, 혼잡도, 작업 인원, 프로젝트, 탈출구 상태를 표시한다.
- 탈출 수가 실패 기준 이상이면 즉시 실패한다.
- 시간 종료 시 탈출 수가 실패 기준 미만이면 성공한다.
- 실패 후 재시작은 최초 8단계 진입 상태를 전부 복원한다.
- 건너뛰기는 확인 없이 9단계로 이동하고 완료로 인정한다.
- 플레이어 사망은 정규 부활 흐름을 사용한다.

### 9단계

- 결정문서의 제공 문구를 그대로 표시한다. 누락된 문장을 새로 쓰지 않는다.
- 재연수와 메인 메뉴 버튼을 제공한다.
- 메인 메뉴 이동 전에 완료 상태를 저장한다.

## 금지 사항

- `T-06`에 따라 단계별 Ready 이벤트, 상태 polling, timeout, 준비 실패 재스폰과 자동 복구를 구현하지 않는다. 0단계 전 전체 학생의 1회 명시적 초기화 계약을 사용한다.
- 8단계 재시작을 위해 DB 전체 학생 풀을 파괴하거나 재스폰하지 않는다.
- 일반 비정상 상태 감지 및 자동 단계 재시작을 구현하지 않는다.
- 튜토리얼을 시작하기 위해 `WaveSystem.NewWaveEntered()`를 호출하지 않는다.
- 정규 인벤토리 장비나 자금을 튜토리얼 세션 데이터로 사용하거나 덮어쓰지 않는다.
- 정규 학생 체력을 1로 낮추지 않는다.
- 3단계 외 학생의 자동 기상을 끄지 않는다.
- 튜토리얼 전용 위험 표식을 만들지 않는다.
- 3단계의 순차 2명 배치를 구현하지 않는다.
- 8단계 학생을 메인 스테이지 스폰 위치로 보내지 않는다.
- 게임 오브젝트 이름, 계층 순서 또는 `Find()`에 의존해 필수 참조를 찾지 않는다.
- 문서에 없는 힌트, 경고, 시간 제한, 실패 조건, 보상과 자동 보정을 추가하지 않는다.
- 사용자 소유의 기존 변경을 되돌리거나 정리하지 않는다.

## 검증 기준

### 정적 검증

- 컴파일 오류가 없어야 한다.
- `git diff --check`를 통과해야 한다.
- 기존 serialized field 값과 정규 asset이 변경되지 않았는지 diff로 확인한다.
- 이벤트 중복 구독과 해제 누락을 확인한다.
- 튜토리얼 참조가 없는 기존 씬에서도 null reference가 생기지 않아야 한다.

### 정규 게임 회귀 검증

가능한 범위에서 다음을 직접 확인한다.

- 메인 메뉴에서 정규 스테이지 선택과 진입이 기존과 같다.
- 준비 시간과 Tab 시작이 기존과 같다.
- 기존 학생 수, 랜덤 로스터, 행동 가중치와 AI 시작 흐름이 같다.
- 기존 학생 피해, 부스터 확률, 패시브 보정과 자동 기상이 같다.
- 기존 바리케이드 초기 상태, 설치, 파괴와 회복이 같다.
- 기존 교수 작업과 이동 중단이 같다.
- 정규 인벤토리 장비, 탄약과 보충이 같다.
- 혼잡도 증가·감소, 프로젝트 보상과 탈출 실패가 같다.
- 정규 성공 후 상점·아레나·다음 웨이브 이동이 같다.
- 정규 재시작, 메인 메뉴 복귀와 저장 데이터가 같다.

테스트할 수 없는 항목은 통과했다고 주장하지 말고, 필요한 수동 검증 절차를 남긴다.

### 튜토리얼 검증

- DB 전체 학생의 행동 런타임 초기화 호출이 모두 반환되기 전에는 0단계가 시작되지 않는다.
- 정규 스테이지 학생은 튜토리얼 초기화 API를 호출하지 않고 기존 애니메이션 이벤트 기반 행동 시작 흐름을 유지한다.
- 단계별 학생 선발과 8단계 재시작에서 Ready 이벤트, polling 또는 학생 재스폰이 발생하지 않는다.
- 단계 전환은 한 번만 발생한다.
- 단계 종료 후 이전 단계 이벤트와 코루틴이 남지 않는다.
- 충성·대기·응원·이동·복귀 학생은 공격과 부스터 영향을 받지 않는다.
- 6단계는 복귀가 완료된 `Standby` 학생만 선택한다.
- 8단계는 출발 지점 Warp 직후 미니웨이브 행동을 시작한다.
- 튜토리얼 진행이 `WaveSystem`, 정규 `InventorySystem`과 스테이지 저장값을 변경하지 않는다.
- 8단계 재시작을 반복해도 상태나 이벤트가 누적되지 않는다.
